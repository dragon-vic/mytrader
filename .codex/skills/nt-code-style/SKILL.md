# 项目代码风格

## 开发方式

本项目采用快速迭代开发方式，不以长期兼容历史代码为目标。

重构时：

- 不需要兼容过去的模块名、函数名、配置格式或文件路径。
- 可以直接删除旧接口、旧文件和重复逻辑。
- 不要为了兼容历史行为增加 wrapper、fallback 或双轨实现。
- 优先建立清晰、稳定、可扩展的新结构。
- 允许直接调整内部接口、配置和目录。
- 迁移完成后删除旧实现，不保留兼容壳。

代码首先服务于当前有效架构，不为已经废弃的设计增加额外复杂度。

## 基本原则

- 实现满足目标的最小设计。
- 保持代码直接、清晰、局部。
- 避免过度抽象。
- 只有在逻辑被多处复用，或抽象能明显降低复杂度时才创建辅助函数或类。
- 不为一次性逻辑创建通用框架。
- 不复制粘贴相同逻辑；真正复用的逻辑放在合理的公共模块。
- 不把不相关的功能混合到同一个模块。
- 优先使用现有框架和项目内已有工具。
- 不引入项目没有必要的新依赖。

## 解耦与可扩展性

- 通用框架不能依赖具体策略的私有字段、文件名、事件名或业务行为。
- `live.py`、`backtest.py` 和 runtime 代码必须保持策略无关。
- 策略差异通过配置、标准接口和组件协议表达，不通过入口脚本中的策略分支表达。
- adapter 只负责交易所或数据源适配，不负责策略业务。
- 报告层只处理通用订单、持仓和运行结果，不读取策略私有状态。
- 前处理、运行控制、报告生成和摘要展示保持独立。
- 模块之间通过清晰的数据结构和函数接口通信。
- 避免循环依赖和隐式全局状态。

## 配置和数据

- YAML 使用结构化类型，不把所有值当作字符串处理。
- 配置解析、校验和组件构建分开。
- 使用 YAML、JSON、Parquet 等结构化格式时，优先使用对应解析器。
- 不通过字符串猜测数据类型、市场类型或策略行为。
- 必需配置缺失时直接报错，不使用静默默认值掩盖错误。
- 不为多个历史格式增加兼容解析逻辑。

## 错误处理

- 错误应尽早暴露。
- 不要捕获异常后只打印日志并继续运行。
- 不要返回 `None` 代表多种错误状态。
- 不要使用 fallback 掩盖配置、凭据或数据缺失。
- 只有在确实需要转换错误边界时才捕获异常。
- 错误信息应说明具体字段、文件或组件。

## 命名和函数

- 命名应能够较好描述功能，避免过短、含义不清的缩写。
- 名称保持适度长度，不写无意义的长句式名称。
- 文件、策略、类、函数和配置字段遵循项目已有命名方式以及 NautilusTrader 的历史习惯。
- 类名使用清晰的名词，函数名使用清晰的动作或结果。
- 函数只做一件主要事情。
- 函数参数不要携带无关上下文。
- 不通过超长函数承载多个生命周期阶段。

## 文件结构

- 目录层级保持浅而清晰。
- 不为了分类创建没有实际边界的多层目录。
- 策略运行需要的代码和配置放在策略目录中。
- 与策略运行无关的研究代码、研究数据、分析图和研究笔记放在对应策略的 `research/` 目录。
- 跨策略复用的数据和工具才放在仓库级目录。

## 注释和文本

- 代码应优先通过结构和命名表达意图。
- 只有不明显的逻辑、外部库限制、历史坑或重要取舍才添加注释。
- 项目代码中的注释使用简短中文。
- 函数用途注释放在函数定义上一行。
- 不写重复代码含义的注释。
- 默认使用 ASCII；已有中文文件可以保持原有字符集。

## 验证

- 修改后执行与改动范围匹配的最小验证。
- 优先直接运行现有入口、配置加载、编译检查或临时 shell 检查。
- 不为了验证而长期保留一次性脚本。
- 验证失败时修复根因，不通过放宽检查掩盖失败。
