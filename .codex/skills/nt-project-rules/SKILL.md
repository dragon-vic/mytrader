# 项目限制和规范

## 项目宗旨与验收优先级

- 策略稳定性和资金安全是开发、审核和上线的首要验收条件。使用杠杆时，验证范围须覆盖敞口放大、保证金不足、单腿成交、部分失败和恢复过程。
- 按策略的时效要求设计性能。套利、微观结构等低延迟策略重点验证峰值行情下的处理能力和尾延迟。中长期策略根据实际决策频率确定性能目标。
- 修改交易、资金或生命周期逻辑时，按风险覆盖正常流程、异常、并发、重复/乱序回报、断连和重启恢复，并审核框架内部的实际行为。沿用下文的线程和真实框架链路验证要求，保留验证结果及发现问题的处置记录。
- 在满足安全、稳定性和时效要求的前提下，保证交易与错误可追溯、可复盘。记录足以还原决策的版本、配置、时间、行情与基线、资金依据、状态转换、订单、成交、费用和错误，并关联到相应阶段、批次和订单。按策略需要选择记录粒度、保存期限和容量上限。
- 高频日志和行情采集采用有界缓冲、异步批量写入等适合负载的方式，避免阻塞交易路径。明确队列满、磁盘满和写入失败的处置并暴露记录缺口。影响重复下单、额度和恢复判断的关键状态应定义持久化确认及失败处理。
- 框架是实现工具。按正确性、性能和可追溯性选择框架组件、独立模块、交易所原生 API 或自定义结构化日志。明确接口、线程归属、启动停止、资源释放及错误传播边界，并验证跨组件链路。

## 测试规则

本项目不需要编写测试模块或长期保留的测试代码。

每次测试使用临时模拟或实际运行流程，按改动风险验证行为正确性、状态一致性及异常恢复：

- 策略测试优先使用 NautilusTrader 回测引擎。
- 框架通用能力使用 `framework_test` 策略验证。
- 测试通常不使用 testnet；默认优先使用真实行情、真实配置和真实框架链路进行验证。
- 是否真实提交订单、使用真实资金或影响正在运行的策略，必须由用户明确确认。
- 不为了测试额外创建长期测试文件、测试模块或测试框架。
- 临时检查使用 shell、内联脚本、回测或一次性运行，完成后清理临时脚本和无复盘用途的产物。
- 验证结论保留覆盖场景、运行环境和版本、结果及待处理事项。运行证据按项目数据规则保存。
- 低延迟链路分别测量行情接收、策略决策、发单、成交和回报处理的耗时，关注峰值流量下的 P99、排队积压与丢失情况。区分本机处理耗时、网络耗时和交易所耗时。
- 不重复运行 live 策略来验证同一个小改动，除非用户明确要求。

## 改动规模和发布

- 小改动默认不创建 commit 或 PR。
- AWS 只有用户明确要求时才同步。
- 用户明确要求同步小改动时，直接同步涉及文件，不自动创建 PR。
- 大改动或完整策略改动才进入 commit、push 和完整验证流程。
- Git 提交、push 和 AWS 同步是分开的动作；没有明确要求时不要擅自同步 AWS。
- 同步 AWS 后说明是否需要重启才能生效。
- 不因为代码已同步就自动重启正在运行的策略、Telegram bot、collector 或其他服务。
- 只有用户明确要求时才停止、重启或替换正在运行的服务。

## Git 和工作区

- Git commit 信息使用中文；标题准确概括目的，正文详细说明主要改动、行为影响和验证结果。
- 尊重用户已有的未提交修改。
- 不回滚或覆盖与当前任务无关的文件。
- 不使用 `git reset --hard`、`git checkout --` 等破坏性命令。
- 提交时只暂存当前任务相关文件。
- 不把 `.env`、API key、SMTP 密码、交易所密钥或运行态报告提交到 Git。
- 服务器通常只是本地已 push 版本的旧版本；检查确认服务器没有额外改动时，pull 或同步应以本地版本覆盖旧版本。
- 不默认 stash 服务器改动。
- 如果服务器存在本地新增文件、未提交修改或真实冲突，且无法明确判断是否应该覆盖，先询问用户。

## 本地和远程命令

- 本地 Windows 使用 PowerShell 7。
- 本地不要调用 Codex CLI；本地邮件链路测试直接使用 Python 标准库和 `.env`，只有用户明确要求时才在本地启动 Codex CLI。
- 本地读取和写入 UTF-8 文件时显式指定 UTF-8。
- 本地 PowerShell 7 不需要使用 Base64 传递普通命令或文件。
- 从 Windows 调用远程 bash 时，只有复杂脚本包含管道、重定向、命令替换或 here-doc 等情况才使用 Base64，避免 shell 转义错误。
- 本地 Python 使用 `D:\app\miniconda\envs\nt\python.exe`。
- AWS 使用 SSH alias `aws`。
- AWS 项目目录为 `/home/ubuntu/pycharm_nt`。
- AWS Python 为 `/home/ubuntu/miniconda/envs/nt/bin/python`。
- 不在未确认目标路径的情况下执行递归删除、移动或覆盖。

## 凭据和实盘

- 不在代码、日志、回答或提交中输出密钥内容。
- 不读取或输出 `.env` 的完整值。
- 只检查凭据是否存在时，不输出具体内容。
- 触碰 live credentials、Conda、系统配置和权限配置前，先说明动作。
- 真实下单、真实资金、实盘重启和生产服务替换必须先得到用户明确确认。
- 使用账户余额、保证金、仓位、PnL 和交易事件前，必须确认当前 adapter 的实际字段映射。
- 资金风控同时核验交易所原始字段语义、数据更新时间及 REST/WebSocket 等更新路径的一致性，结合在途订单预留处理重复占用和更新滞后。
- 保证金、可用余额及策略资金分配由项目独立模块处理，以交易所原始账户接口为依据。阶段内用本地订单预留、实际成交、手续费和盈亏记账，保留快照来源与时间。
- 已重复遇到 Binance U 本位余额映射问题。本地 NT 1.230.0 的 REST 路径读取 `availableBalance`，账户 WebSocket 路径却将钱包余额 `wb` 写入 `free`，并将 `locked` 置零，后续事件会覆盖可用余额。策略资金风控禁止使用框架的 `balance_free` 或钱包余额代替原生可用保证金。框架升级时核验映射和更新链路，独立资金管理继续承担风控职责。
- 不能用测试账户余额、模拟数据或空值接口假设真实风控字段有效。

## 策略代码生命周期注意事项

编写或检查由行情、定时器和订单事件反复驱动的策略时，注意避免生命周期错误造成重复或过量下单：

- 区分“价格处于阈值外”和“一次阈值触发事件”。一个交易阶段完成后保留完成状态；确实需要再次触发时，再设计明确的重新武装条件或滞回区，避免价格在阈值附近波动时连续开启新阶段。
- 提交订单前记录当前批次的 pending 状态，双腿完全成交后再推进下一步，并注意不要由重复定时器或无关订单事件重复推进。
- 计算仓位时考虑 NT 可能把交易所净仓拆成多个 position ID。先聚合 signed quantity 得到净仓，再计算方向和名义价值，不要把各 position 的绝对值相加后当作实际净仓。
- 每次下单前检查累计轮数、目标金额、实际净仓和数量；零仓、尾仓或数量为零时应正常结束流程。
- 修改这类状态逻辑后，按风险做针对性验证，至少留意阈值持续满足、阈值附近来回穿越、部分成交和重启后的行为。
- 实盘LiveClock回调按跨线程处理，先通过event loop调度再访问策略、订单、持仓、文件与采集器状态；关键状态入口检查线程归属。新增私有方法前核对NT Actor/Strategy基类名称与签名，避免覆盖框架生命周期方法。涉及首次开仓、退出或状态保存的修改，必须使用真实LiveClock和模拟执行客户端验证，回测和纯行情压测分别验证其他路径。
- 更改执行方式时一起检查开仓、补齐、正常平仓、强制清仓，按实际盘口与收益空间解释滑点预算。分批下单每批重新验证信号、深度与实际仓位；区分可以暂停/反转决策的正常退出与锁定执行的风险清仓。用户允许部分平仓后重新加仓时，用实际释放额度控制新增持仓，并验证单腿未完成时不会重叠发单或提前释放额度。
- 常见网络超时、行情陈旧、只读接口失败和临时交易暂停采用暂停新增风险、查询核单及恢复流程。保留已匹配对冲，按正常回归条件减仓。订单超时保留 pending，确认成交结果后处理。强制清仓用于明确收盘/公司行动窗口、无法修复的单腿风险或关键状态损坏。已知开仓拒单先补齐对冲，成功后保留仓位并暂停本阶段加仓，补齐失败才清仓暂停组合。

## 框架通用性

- `backtest.py`、`live.py`、`run.py` 和 `utils/` 不得为具体策略写分支。
- 通用代码不能读取、猜测、转换或依赖策略私有文件和事件。
- 策略差异通过配置、标准组件接口和明确协议表达。
- 策略不能 import 通用报告 writer。
- 报告层不能依赖某个策略的私有状态。
- 外部 actor、data client、adapter 和 runtime 不能绑定某个策略的内部实现。
- 外部组件之间需要通过明确的数据契约通信。
- 新增或删除策略、通用模块、入口或关键运行组件时，必须同步更新 `nt-project-context` 和受影响的项目 skill。

## 命名和目录

- 文件、策略、类、函数和配置字段应较好描述功能，长度适中，不使用含义不清的短缩写或无意义的超长名称。
- 命名遵循项目已有方式和 NautilusTrader 的历史习惯。
- 目录层级保持浅而清晰，避免过度嵌套。
- 策略运行无关的研究代码、研究数据、分析图和研究笔记统一放在 `strategies/{strategy_name}/research/`。
- 跨策略复用的代码和数据才放在仓库级 `tools/`、`utils/` 或 `data/`。

## 工具规则

- `tools/` 下的工具默认独立调用。
- 工具不自动接入策略、Node、actor 或策略生命周期。
- 只有用户明确要求时，才把工具接入策略或框架。
- 工具不应隐式读取策略私有状态或依赖策略文件格式。

## 配置规范

- 共享默认配置放在 `strategies/global.yaml`。
- 策略配置放在 `strategies/{strategy_name}/`。
- live 配置不能依赖回测专用数据字段。
- 回测数据集、合成 instrument、费率、保证金和账户设置属于回测配置。
- 必需参数必须在有效 YAML 中声明。
- 配置缺失、类型错误或未知字段应直接失败。
- 不在 factory 中硬解析 YAML 字符串来猜测业务含义。
- 不添加多套等价配置格式。
- 不添加历史配置兼容层，除非用户明确要求。
- 交易所市场规则由对应 adapter 负责解释。
- 参数类型转换应由配置 schema、策略 config class 或结构化解析层负责。

## 交易所规则

- 默认交易所为 Binance，除非用户明确指定其他交易所。
- 不把某一个交易所的行为写入通用策略或入口逻辑。
- Binance U 本位账户事件使用精确 topic：
  `events.account.BINANCE-USDT_FUTURES-master`
- OKX client order ID 不允许包含 `-`。
- 交易所 adapter 不负责策略逻辑。
- 交易所接口和余额映射变化时，先检查当前 NautilusTrader 版本和 adapter 实现，再运行验证。

## 停止和生命周期

- Node 停止必须通过明确的停止协议。
- 策略内部请求停止时，Node 负责执行统一停止流程。
- Node 停止后的报告、summary 和 artifact 仍由统一后处理生成。
- 不在策略中直接调用报告写入工具。
- 不修改大型框架生命周期来解决单个报告格式问题。
- live、testnet、backtest 的前处理、运行和后处理职责保持分离。
- 运行目录应由 runtime 创建和传递，不由策略自行猜测项目根目录。

## 代码和依赖限制

- 不使用 argparse 作为项目任务分发器。
- 入口保持在根目录，策略保持在 `strategies/`。
- 不为了小功能修改 NautilusTrader 核心生命周期。
- 不静默安装依赖。
- 缺少依赖时先说明包名和安装目标环境，确认后再安装。
- 除非用户明确要求，不更新 README。
- 不创建无实际用途的 package 层或重复目录。
- 不使用空值、零值或 fallback 伪装接口可用。
- 允许删除旧代码和旧接口，不需要为历史实现保留兼容 wrapper。
